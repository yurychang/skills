# UI 介面優化

改善使用者完成任務的路徑，讓介面清楚、一致且容易操作。以現有產品為基礎，不把「優化」自行擴張為新增功能或更換技術。

## 確定目標與可用證據

- 先讀專案指引，辨識實際產品入口、目標畫面、元件庫與樣式來源。區分正式介面、展示範例和已停用的舊來源，避免改錯入口。
- 從使用者描述、截圖、程式碼或可操作畫面建立目前狀況。目標可從上下文確定時直接進行；有多個合理目標且會改到不同範圍時，才詢問要優化哪一處。
- 「審查／建議」交付具體問題與改法；要求「優化／修好」且已有可編輯專案時，落實修改並驗證。只有截圖時提供依據畫面的分析，不把想像的控制項或行為當成事實。
- 確認這個畫面的主要任務與既有行為。若沒有指定風格，延續現有產品與平台慣例；不要求使用者先選色盤、字體或設計流派。

## 讓問題帶動改動

先處理阻礙完成任務、遺失內容或無法操作的問題，再處理資訊混亂、視覺層級與裝飾細節。每個主要改動應能說明：哪個情境出問題、使用者受到什麼影響，以及修改後可觀察到什麼改善。不要為湊滿審查清單而製造問題。

### 先解決整頁結構，再調整局部

辨識主要任務及操作頻率。若相關控制分散、同一操作逐卡重複、簡單選項占用大型卡片，或初始畫面被說明擠滿，先重組資訊與操作路徑；不能只搬動按鈕、縮短幾句文案或調整間距就結案。依內容選擇緊湊清單、單一詳情區或其他適合的模式，不把某次提案的雙欄當成所有畫面的固定解法。

### 審查視覺美觀並生成示意圖

除了可用性，也要從視覺美觀的角度審查排版與元件樣式：檢查比例、留白節奏、對齊、文字層級、內容密度，以及控制項的尺寸、邊框、圓角、色彩與狀態是否協調。指出具體畫面中的問題，並提出可用現有技術、元件庫與設計 token 落實的優化建議，不以更換技術棧作為視覺改善的前提。

凡提出或實作視覺優化，必須生成並展示示意圖，包含建議的排版與元件樣式，讓使用者能直接判斷視覺效果；不能只交付文字建議、程式碼或未渲染的線框描述。可使用現有畫面的標註或改稿、渲染後的 mockup 或其他適合的圖像，明確標示為提案示意，不能當成正式產品已實作或已驗證的證據。

使用者明確要求先看方案時，先交付示意圖；其餘在任務中提供示意圖，並依已授權範圍直接實作與驗證，不額外設置方案核准關卡。

### 讓每段提示有存在理由

逐段判斷提示是否影響當下決策。刪除重複標籤、顯而易見的操作解釋及常駐的冗長說明。字數限制可在接近上限或驗證失敗時呈現，補充說明可按需展開；必要的前置條件與風險仍要簡短可見，並附適用的處理入口。不要把刪掉的段落換成同樣冗長的 tooltip。

### 用一致的分組容納相關設定

相關偏好放在有明確名稱的設定區，沿用一致的標籤與控制項排列。若一個偏好未來可能有同類選項，不應只因頁首有空間就把它孤立放在角落；檢查增加一個合理同類選項時能否沿用相同排列即可，不新增虛構設定、預留空白或擴充框架。建立副本、瀏覽內容與改變預設的語義要清楚，避免無意間改動使用者選擇。

依畫面需要檢查：

- **主要操作與分組：** 主要動作是否容易找到；標籤是否表達使用者目的；次要或進階設定能否適當收合。收合後仍要能發現目前設定、錯誤與必要控制項。
- **清單與詳情：** 摘要應方便掃描，查看後立即呈現對應內容；不能只改成「已選取」卻把詳情放在長清單尾端。返回應保留搜尋、適當位置與來源項目焦點。完整內容的複製等常用操作，不應被所有進階選項推到下方；空搜尋結果也不能當成全域資料為空。
- **資訊與視覺層級：** 透過現有字級、間距、對齊與語意色建立主次。先調整分組及重複層級，再考慮額外容器；不預設每個區塊都要做成卡片、加陰影或漸層。
- **表單與回饋：** 分清草稿、已保存、處理中、失敗與未知狀態。錯誤要指出可處理的欄位；跨分頁錯誤應能帶到相應位置。新編輯之後，舊成功提示不能繼續暗示內容已保存。回饋應對應實際動作，分清請求已受理與工作已完成；在長頁底部操作時，也應能看見進行中或失敗原因，不把回饋留在使用者看不到的頁首。
- **內容與尺寸：** 使用合理的長文字、空清單、錯誤訊息及動態新增項目檢查布局。固定頁尾、工具列與浮層不能遮住操作或焦點；捲動區要能實際到達最後一項。條件隱藏的區塊不應留下意外空白。
- **鍵盤與可及性：** 核對焦點可見、導覽順序、控制項名稱及狀態辨識。錯誤不能只靠顏色表示。檢查實際文字與背景的對比，不因為 token 名稱帶有 danger 或 muted 就認定可讀。

## 在既有架構內實作

優先使用專案的標準元件、語意 token 與版面慣例。只有重複出現且確有共用價值的部分才抽成 helper；單頁微調不需要另建設計系統、路由或樣式框架。網頁與原生 App 各自使用既有技術，不用 HTML 展示頁取代原生產品修改。

捲動條（scrollbar）只能使用平台原生或現有框架／元件庫內建功能，樣式調整也使用其支援的介面。不可自行繪製軌道、滑塊或實作拖曳、位置同步來仿製捲動條；現有能力不足時保留標準行為，並說明限制。

重排前後核對原控制項、資料綁定與事件回呼。調整文字、順序或分組時，保留已有能力；若某項移除或預設值變更會影響行為，應有明確任務依據。

特別保護會因重排而回歸的狀態：

- 切頁、收合與重新整理保留未保存草稿、選擇及適當的捲動位置；不可藉重新建立元件悄悄重設狀態或觸發保存。
- 動態清單使用穩定身分。新增項目應能被找到並編輯；刪除有焦點的項目後，焦點移到合理且可見的位置。
- 除非使用者明確要求，避免新增自動捲動功能；新增項目、焦點或驗證事件本身不構成授權。優先用版面安排及可見回饋解決可發現性，保留既有必要的鍵盤導覽與捲動位置恢復。已要求的自動捲動也須限於對應事件，背景刷新與延遲回呼不可反覆搶回捲動或覆蓋使用者之後的焦點。
- 更改 Tab、快捷鍵或多行輸入行為時，保留輸入法組字與文字編輯語意，不把一般導覽處理套入尚未完成的組字。

## 以實際畫面驗證

使用目前允許的檢查方式。已有暫停測試、受限應用或資料隔離規則時，遵守該界線；本技能不授權恢復測試或操作真實帳號資料。

選擇能揭露這次風險的情境，不機械地展開全平台矩陣：重排表單就查草稿與保存，固定頁尾就查最後一項和焦點，動態清單就查新增及刪除後的導覽。依目標平台檢查適用的視窗尺寸、縮放或主題；未實測的條件保持未驗證。

UI 實作後要查看修改後的實際產品畫面，並操作受影響的流程。來源審查、單元測試、建置或封裝成功只能補充證據，不能取代這項驗證。交付說明須如實反映已做的檢查，不可暗示未執行的畫面或操作驗證已通過。

- 修改前先查看目標畫面並記錄具體問題；修改後使用包含本次變更的建置，確認版本或來源身分及實際開啟的頁面，避免誤驗仍在執行的舊版 App。
- 使用可用且允許的瀏覽器或原生介面工具，實際查看渲染結果或擷取畫面並檢視內容。只啟動 App、產生截圖檔或讀取元素樹，不代表已檢查畫面；原生 App 必須查看原生產品，不能以 HTML mockup 或獨立 demo 替代。
- 在可比較的資料與視窗條件下核對前後結果，實際操作本次改動涉及的控制項。例如重排表單就操作編輯、切頁與保存；新增導覽入口就點擊確認目的頁與草稿保留。畫面仍有遮擋、截斷或狀態錯誤時，修正後再查看受影響路徑。
- 動態元素必須在狀態變化時檢查 Layout Shift（版面位移），不能只看切換前後的靜態畫面。依改動操作載入／完成／失敗、提示出現／消失、按鈕文字與禁用狀態、展開／收合或清單增刪，觀察切換前、過程中與完成後，核對周邊內容及操作目標是否意外跳動、換行或改變可見位置，並留意捲動條出現／消失造成的寬度變化。區分預期的內容展開與非預期位移；必要時使用穩定尺寸、合理預留空間或框架既有布局能力修正，不靠新增自動捲動掩蓋問題。記錄觸發狀態、位移位置及修正後觀察；只有靜態證據時，狀態轉換仍屬未驗證，不能只以網頁 CLS 分數判定通過。
- 在修改前先提出這次版面要改善的可觀察判準，例如主要選項在初始畫面是否可找到、比較選項是否減少捲動、重複操作與無效留白是否減少、相關控制是否更集中。修改後以同等條件的整頁畫面逐項核對；「沒有遮擋」及「按鈕能點」只是基本檢查，不能單獨證明資訊層級或操作效率改善。若原本的主要問題仍存在，繼續調整，不以新增說明文字掩蓋。
- 留下可定位的畫面證據及簡短觀察，記錄建置身分、視窗尺寸與已檢查情境；截圖不得洩漏金鑰或私人內容。靜態截圖不能證明操作成功，合成輸入也不能證明真實輸入法或實體鍵盤正常。

若缺少工具、無法啟動、測試被暫停或受權限限制，先完成仍可進行的實作與檢查，交付時備註無法進行實際畫面驗證的原因、未驗範圍與適用的後續方式，不需加上「尚未完成」狀態標籤。只有確實需要額外授權時才詢問；不得擅自恢復測試、繞過限制，或把環境限制當成驗證通過。

沿用專案要求的檢查。只有行為邏輯改變或存在具體回歸風險時，新增有意義的測試；不為間距、文案或樣式常數撰寫逐字比對測試。

## 獨立審閱與迭代

使用者要求獨立審閱時，由主 Agent 負責設計與實作，另用獨立 sub agent 依本技能審閱。一般小幅調整不因此一律要求委派。

向審閱者提供使用者目標、既有限制、變更範圍及可定位的來源、前後畫面與操作紀錄；讓審閱者自行判斷問題，不預設結論。審閱者須親自查看修改後畫面，分清自己觀察的畫面、實作者回報的操作及僅由來源推測的風險；不能只轉述實作者的檢查結果就宣告通過。

先修正影響主要任務、內容保留、可見操作或狀態正確性的阻擋問題，再以包含修正的建置驗證受影響路徑並送回審閱。已知阻擋問題皆已解決時可收斂，非阻擋建議不必變成無限美化。通過結論必須列明本輪實查的畫面與條件；缺少證據或未獲授權的測試維持未驗，不能擴大成整個 App 或所有環境皆通過。

## 交付

說明主要改善、對應使用情境、驗證結果及仍未驗證的部分，提供可定位的檔案或畫面證據。視覺優化須附生成的示意圖，並與修改後的實際產品畫面證據分開標示；涉及動態元素時，交代已檢查的狀態切換與 Layout Shift 觀察。使用使用者的語言；沒有其他偏好時以繁體中文回覆與撰寫新增文案。

若專案要求打包交付，完成適用的建置與封裝，再報告產物。區分原始碼已修改、套件已產生、應用程式已安裝或重新啟動，不能以其中一項暗示其他項目完成。
